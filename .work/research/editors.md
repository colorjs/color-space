# editors

## summary
I wrote <session-scratch>/research/editors.json with 9 entries: CapCut desktop, CapCut mobile, DaVinci Resolve, Premiere Pro, Final Cut Pro, OBS Studio, ffmpeg, LumaFusion and VN. Each entry has id, name, platforms, steps, accepts1D, accepts3D, maxSize, notes and source. Inside the notes, every fact is tagged with how it was checked. accepts1D/accepts3D are null where I could not verify them.

**What is verified and how:**
- **ffmpeg and OBS:** both are open source, so I read their code and docs on raw.githubusercontent.com. I also ran the ffmpeg build installed here (6.1.1) on .cube files generated by this repo's lut.js.
- **Resolve's .cube format:** read in full from a Blackmagic staff forum post quoted inside the OpenColorIO source.
- **CapCut, Adobe, Apple, Luma Touch, VN and Blackmagic's own pages:** the sandbox proxy blocked all of them, so their menu paths come from search-result snippets, labelled as such.

**Findings that matter for the site's "camera log → editor" flow:**
1. **OBS would likely crash on the library's default 1D cube.** For a 1D LUT, OBS still sizes its buffer as if the LUT were 3D, and the size calculation overflows to zero bytes for 1D lengths of 1024 or more. OBS's allocator aborts the program on a zero-byte request. lut.js writes LUT_1D_SIZE 4096 by default for channel-by-channel pairs, and its shaper option writes a 1024-entry shaper. I confirmed the arithmetic by compiling OBS's exact expression with gcc. I did not run OBS itself. The same code is in OBS 28.0.0 through 32.0.0 and current master.
2. **OBS misreads shaper cubes.** If a file declares both a 1D and a 3D size, OBS loads only the 1D part. It also ignores Resolve's LUT_3D_INPUT_RANGE line and only understands DOMAIN_MIN/DOMAIN_MAX. It skips the filter for HDR sources.
3. **ffmpeg applies shaper cubes wrongly without any error.** It skips the shaper and applies only the 3D part. Measured against the direct conversion, the error was 8.6 8-bit codes on average (worst 213), versus 0.06 for a plain 33³ cube.
4. **ffmpeg has two separate filters.** lut3d rejects a 1D cube ("3D LUT is empty") and lut1d rejects a 3D cube ("1D LUT is empty"). Limits are 2–256 for lut3d and 2–65536 for lut1d; a size of 257 is rejected. Default interpolation is tetrahedral for lut3d and linear for lut1d.
5. **Windows paths in ffmpeg** only work as `lut3d=file='C\:/x.cube'`. I tested the other obvious spellings and they all fail.
6. **LumaFusion's only documented size limit is "up to 64 points"** (a 2017 release note), so a 65³ cube is above it.
7. **Resolve reads 1D-only, 3D-only and shaper+3D cubes.** It is the only editor here confirmed to read the shaper format.
8. **Final Cut Pro:** Apple documents ".cube and .mga" 3D LUTs and no size limit.
9. **Premiere 25** offers Input LUT in three places, including Lumetri Color > Settings > Source Clip.

**Not verified:**
- CapCut: whether it accepts 1D cubes, and its maximum size.
- CapCut mobile: only third-party guides say it has no custom LUT import; CapCut's own pages say nothing either way.
- Premiere and Final Cut Pro: whether they accept 1D cubes, and their maximum size (users report 65 points works in Premiere).
- VN: whether 1D cubes or desktop import work, and its size limit.
- Resolve: the maximum size it will import, and the Linux folder path, where sources disagree.

## recommendation
For the creator flow on color-space.io:

1. **Make one file the default:** a plain 3D .cube, 33 points, with a single LUT_3D_SIZE line, no shaper, the default 0–1 range (or DOMAIN_MIN/MAX), and header lines under 256 bytes. That file is within what every editor's documentation (or code) allows: CapCut desktop, Resolve, Premiere, Final Cut Pro, OBS, ffmpeg lut3d, LumaFusion (64-point limit) and VN.
2. **Offer 65 points only as a "high precision" option** for Resolve, Premiere, Final Cut Pro, OBS and ffmpeg. Do not offer it for LumaFusion, whose documented limit is 64.
3. **Force 3D whenever the target is an editor.** lut.js currently writes 1D cubes (LUT_1D_SIZE 4096) for channel-by-channel pairs by default. OBS would crash on that file, according to its source, and ffmpeg would need lut1d instead of lut3d. CapCut, Premiere, Final Cut Pro and VN have no documented 1D support. Either pass dims:3 in the editor flow, or keep 1D only for an explicit ffmpeg lut1d download. The comment at lut.js:274 says the .cube output works in OBS and ffmpeg, which is only true for 3D files and should be corrected.
4. **Label the shaper cube "DaVinci Resolve / OCIO only".** ffmpeg applies it wrongly without warning, and OBS misreads it (and per its source would crash on the 1024-entry shaper). Warn about this rather than just saying "not supported".
5. **Per-editor tips to show on the page:**
   - Resolve: tell users to click Open LUT Folder rather than copying to a hard-coded path, especially on Linux.
   - Premiere: point to Input LUT (not Creative Look), and warn about converting log twice under Premiere 25's color management.
   - Final Cut Pro: Custom LUT effect with its Input/Output color spaces set, or Camera LUT.
   - OBS: Amount at 1.0, and note that it works on SDR sources only.
   - ffmpeg: give a copy-paste lut3d command with interp=tetrahedral and the Windows `'C\:/'` path form.
   - CapCut: desktop only. Do not promise mobile import or 1D support.
6. **Before shipping**, test-load the 33 and 65 files once in CapCut desktop, Premiere, Final Cut Pro, LumaFusion and VN; their limits come only from snippets or third parties. Also try the 1D 4096 file in a real OBS to confirm the crash I inferred from the source.

## skeptic overall
I re-checked all 13 claims; 11 hold and 2 are refuted. The researcher's cubes are byte-identical to fresh lut.js output.

Confirmed from fetched source and runs of ffmpeg 6.1.1:
- **FFmpeg limits and formats:** lut3d sizes 2..256, lut1d sizes 2..65536, formats chosen by file extension, default interpolation tetrahedral (3D) and linear (1D), and the "LUT is empty" errors for the wrong dimension all match.
- **FFmpeg Windows paths:** all four drive-letter escaping results reproduce. Two more forms also work: unquoted `C\\:` and the positional `lut3d='C\:/x.cube'`.
- **OBS:** the parser, allocation overflow, UI strings and shader match at master and tags 28.0.0–32.0.0. The menu path is now confirmed from OBS's own frontend source, not just search results.
- **Resolve:** the `.cube` format description is accurately quoted in OpenColorIO's source. The folder paths are supported by several independent sites, though not by Blackmagic's own pages (blocked).

Refuted:
- **Shaper cube error figures:** the numbers can't be reproduced, and the researcher's test script wasn't saved. ffmpeg does accept the file and silently ignores the shaper. On all 2^24 8-bit codes I measured: shaper cube mean 33.8 codes (max 217), plain 33³ cube mean 0.38 (max 255). The plain cube's 255 is ordinary lattice error in steep out-of-gamut corners.
- **Longest line:** 205 bytes is true for one file only. A sweep of 4,044 cubes reached 208 bytes, and all pairs without the verification comment peak at 193. Every line is still under OBS's 255 and ffmpeg's 511 limits. No BOM, LF line endings.

New finding (most important):
- **color-space's shaper:true cube is broken in OpenColorIO 2.6.0.** OCIO's Resolve reader rejects any `TITLE` line, and the generic `.cube` reader rejects `LUT_3D_SIZE` coming after the shaper data. OCIO then silently falls back to a reader that drops the shaper: input 0.5 gives 0.5 instead of 0.641, mean error 34 codes. With only the `TITLE` line removed it reads correctly (mean 0.15, max 5.9 codes).
- So the comment in lut.js, "DaVinci Resolve / OCIO (resolve_cube)", is wrong for OCIO. The Blackmagic text also says both size lines should come before any data, which color-space doesn't do. Whether Resolve itself accepts the file can't be checked here.
- Suggested fix in lut.js: when the shaper is on, omit `TITLE` and write `LUT_1D_SIZE` and `LUT_3D_SIZE` together before any data.

Minor extra:
- **ffmpeg DOMAIN lines:** lut3d silently ignores a `DOMAIN_MIN`/`DOMAIN_MAX` line placed before `LUT_3D_SIZE`. color-space doesn't emit these lines, so it doesn't affect us.
- **Resolve, Mac App Store build:** it reads LUTs from `~/Library/Containers/DaVinci Resolve/Data/Library/Application Support/LUT`, not `/Library/...`. Advise users to use "Open LUT Folder" on every platform.
